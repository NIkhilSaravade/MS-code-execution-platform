# Known Limitations & Future Scope

A single, honest inventory of what this project's AI-review upgrade (docs/ai-agent-build-log.md,
Phases 1-6) does *not* yet do, collected in one place instead of scattered across phase commit
messages. Each item here was disclosed at the time it was found, not discovered by an outside
reviewer later — this doc exists so that stays true going forward: update it in place as items
close, don't let it drift into aspiration.

## 1. Evaluation set size (n=5)

Phase 3's golden dataset has 5 hand-authored problems (two-sum, valid-parentheses, max-subarray,
is-palindrome, fibonacci-memo), each Python, each with one hand-authored mutation covering a
single bug class. Phase 6's base-vs-fine-tuned comparison (`results/finetune_eval.json`) —
60% vs 40% catch rate — is therefore 3-vs-2 cases, not a statistically meaningful claim. Say so
plainly if asked; a percentage on n=5 implies more precision than the sample supports.

Two compounding narrowness issues, not just the count: every case is Python, on a platform that
judges 7 languages, and mutations are hand-authored per problem rather than generated by a
general-purpose mutation-testing tool (the original Phase 3 scope note already flagged this).
False-positive detection is a keyword heuristic, not a semantic classifier, so the 0% false-positive
rate is weaker evidence than it looks.

**What closing this looks like:** grow the dataset using the platform's own problem bank
(`problem-service`/real accepted submissions) instead of hand-authoring more from scratch, stratify
across languages, and replace hand-authored mutations with a real mutation-testing tool per
language (`mutmut`/`cosmic-ray` for Python, PIT for Java). Report a confidence interval alongside
the catch rate once n grows, rather than a bare percentage. Target: 30-50 examples is a real jump
in statistical footing without needing hundreds — that volume matters for the fine-tuning training
set (below), not this regression eval.

## 2. RAG retrieval: reranking did not help (negative result, not fixed)

Phase 2's required A/B eval (`scripts/eval_retrieval.py`) showed hybrid search + cross-encoder
reranking making precision *worse* on the hand-labeled query set: precision@3 0.333 → 0.312, MRR
1.000 → 0.953. Root cause traced to one adversarial query the cross-encoder misranked, and to the
141-chunk corpus already sitting near a precision ceiling for vector-only search — reranking had
little room to help. This was shipped and documented honestly rather than reverted or hidden; the
reranker is live in `services/reranker.py` but is not currently proven to improve results.

**What closing this looks like:** grow the corpus past 141 chunks (more real docs/anti-patterns),
re-run the A/B eval, and specifically investigate the adversarial query that the cross-encoder
misranked before concluding reranking is or isn't worth keeping.

## 3. Fine-tuning: did not beat the base model (negative result, not fixed)

Phase 6's real GPU LoRA fine-tune (Qwen2.5-Coder-3B-Instruct, QLoRA, 508 examples: 460 mined real
PR review comments + 48 synthetic critic-gated examples) did not beat the base model on Phase 3's
eval set — 60% (base) vs 40% (fine-tuned) catch rate, though it did fix a JSON-schema-shape bug the
base model had (1 parse failure → 0). Eval loss got worse after epoch 1 (0.944 → 0.946 → 0.995),
a real overfitting signal on this dataset size — the best checkpoint (end of epoch 1) was used, not
the final one. Plausible causes (dataset dominated by placeholder-heavy fields, tiny eval set,
early overfitting) are disclosed as hypotheses, not proven.

**What closing this looks like:** more real mined data (currently 460 real examples — more source
repos, longer date range), a cleaner real:synthetic ratio, and re-running the same eval once
Limitation #1's larger eval set exists — a 5-case eval set is also too small to trust *this*
negative result strongly in either direction.

## 4. Observability: 2 of 10 services instrumented

OTel tracing exists only on `ai-analysis-service` and `worker-service-go` (`infra/otel/`). The
other 8 Java Spring Boot services (api-gateway, auth-service, user-service, problem-service,
submission-service, execution-result-service, solution-service, discovery-service) have structured
logging but no distributed tracing — so a request that spans multiple services has no single trace
to follow across them today, only per-service logs correlated by eye.

This was an explicit, disclosed scope decision in Phase 6 (the session's remaining time went
entirely into making the LoRA fine-tune real instead), not a silently dropped requirement.

**What closing this looks like:** add the Spring Boot OTel Java agent to the remaining 8 services
(mechanical but real work across 8 codebases) and confirm cross-service trace correlation actually
works end to end, e.g. a submission's full path from `submission-service` through Kafka to
`ai-analysis-service`.

## 5. Deployment: CD gap (in progress)

Deploying a new image onto the k3s cluster today is still a manual `git pull` +
`kubectl rollout restart deployment/<name> -n platform` on the Oracle VM (see
`docs/14-DEPLOYMENT-OPERATIONS-RUNBOOK.md`). CI (build, push, tag, selective per-service builds) is
fully automated already; only the "apply this to the cluster" half is manual. This gap is
pre-existing and self-documented (`docs/06-CI-CD-PIPELINE.md`), which already names the intended
fix: ArgoCD watching the `release` branch and applying `infra/k8s/*.yaml` automatically, with CI
writing the new image tag into that branch's manifests after a successful push.

**Status:** scoped, not yet implemented as of this doc. Update this section once ArgoCD is live —
this should become the first limitation in this document to move to a "resolved" note rather than
staying open.

## 6. Frontend: now consuming the upgraded backend (closed, with real caveats)

Was: confirmed directly in `frontend/src/api/submissions.ts` that it only polled
`GET /ai/analysis/{id}` in a loop for a static PENDING/READY result, never called
`POST /ai/analyze/stream`, had no `429` handling, and surfaced none of the new backend
capabilities.

**Closed**: `api/submissions.ts` now has `streamAiAnalysis` (a hand-rolled SSE reader over
`fetch()` + `ReadableStream` — `EventSource` can't POST a body/Bearer token, so it isn't usable
here) and `isRateLimitError`; `api/client.ts` now throws a real `ApiError` subclass (still
`instanceof Error`, so every existing catch block keeps working) carrying the HTTP status, which
is what makes 429 detectable at all. `SolvePage.tsx`'s Run/Submit flow now streams a fresh review
live (`runAiAnalysisStream`) instead of polling for the Kafka-auto-triggered one, and the
AI-analysis tab shows: the raw JSON building up token-by-token while streaming, badges for which
tools fed the review (`run_linter`/`run_security_scan`/etc.), "Referenced: ..." citation chips for
any `fetch_similar_past_reviews` knowledge-base hits, and a verified/not-yet-verified badge driven
by `criticVerdict === null` (unambiguous — the critic never returns `null` for an analysis it
actually checked, even a plain approval).

**The type audit this item asked for**: done, by re-reading `services/analysis_pipeline.py` and
`main.py` directly rather than guessing. It found something worth fixing on the backend, not just
the frontend — `GET /ai/analysis/{id}` and `POST /ai/analyze`'s cache-hit path were NOT returning
`toolCalls`/`criticVerdict`/`revised` at all, because `AnalysisCache` only ever persisted the raw
LLM response text, not that metadata. Added an `AnalysisCache.metadata_json` column
(`db/models.py`) and wired it through `analysis_pipeline.py`'s read/write paths and both `main.py`
endpoints, with a real SQLite round-trip test (`tests/test_analysis_pipeline_metadata.py`) proving
the data survives a write-then-read cycle, not just a mocked call. One disclosed migration gap:
`Base.metadata.create_all` only creates missing tables, not missing columns on an existing one -
an already-deployed `ai_analysis_db` needs a manual `ALTER TABLE` to pick this column up.

**Real caveat carried over, now visible in the UI rather than just in this doc**: the critic pass
(Phase 5) still only runs on the non-streaming path — a live-streamed review shows the
"not yet verified by a second AI pass" badge, honestly, rather than claiming a verification that
didn't happen.

**Not done, disclosed rather than glossed over**: this was verified via `tsc --noEmit` (clean),
`oxlint` (clean), a full production build (`npm run build`, succeeds), and a dev-server boot check
- NOT against a live backend in an actual browser session, since Docker Desktop wasn't running in
this environment and standing up the full stack (8 Java services + Postgres + Kafka + MinIO + this
Python service) was out of scope for this pass. Click-through verification against the real running
app is a real gap, not a formality — do that before treating this as fully proven.

## 7. Streaming + critic composition

Documented in `docs/ai-code-review-architecture.md`: `analyze_stream()` doesn't compose cleanly
with the critic's "throw the draft away and redo it" revision model without a bigger SSE protocol
change (e.g., a revision would need to retract already-streamed tokens on the client, which SSE
doesn't support natively). Logged as a real, disclosed follow-up in Phase 5, not silently skipped.

**Partially closed**: the frontend now takes the second option above rather than the SSE-protocol
option - it accepts the tradeoff and exposes it, showing a "not yet verified by a second AI pass"
badge on every streamed review (see item 6) instead of pretending the critic ran. What's still
open: there's no user-facing way to ask for the slower, critic-verified path instead (e.g. a
"verify this" button that calls `POST /ai/analyze` after the stream finishes) - today the tradeoff
is fixed, not actually a choice the user gets to make.
